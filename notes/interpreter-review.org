* High confidence

** environment.sld — =pure-raw= arity error messages are swapped (lines ~1477-1479)

#+begin_src scheme
(cond
 ((> count n) (eval-error "not enough arguments" sym n args))
 ((< count n) (eval-error "too many arguments" sym n args))
 (else (apply proc args)))
#+end_src

You wrote =(> count n) => "not enough arguments"= and =(< count n) =>
"too many arguments"=, which is wrong because =count= is the actual number
of arguments and =n= is the number expected: =count > n= means /more/ than
expected (too many), and =count < n= means /fewer/ than expected (not
enough). The two messages are backwards. You probably intended:

#+begin_src scheme
(cond
 ((> count n) (eval-error "too many arguments"  sym n args))
 ((< count n) (eval-error "not enough arguments" sym n args))
 (else (apply proc args)))
#+end_src

This affects every builtin defined through =pure=, =pure-raw=, =pure=,
=type-predicate=, e.g. calling =(cons 1)= reports "too many arguments" and
=(cons 1 2 3)= reports "not enough arguments". Not caught by the tests
because no test passes the wrong number of arguments to a =pure-raw=
builtin.

** elisp-eval.sld — =eval-unintern= never touches the environment (lines 2218-2222)

#+begin_src scheme
(define (eval-unintern st name)
  (update&view
   (lambda (obj) (if (not obj) (values #f #f) (values #f #t)))
   (=>env-obarray-key! name)
   ))
#+end_src

You wrote =(update&view updater (=>env-obarray-key! name))=, which is wrong
because =update&view= has signature =(update&view updater record-in-focus
. lenses)=. Here the lens =(=>env-obarray-key! name)= is being passed as
the *record-in-focus* with *no lens following it*, so =compound-update=
just applies the updater to the lens object itself (a truthy value) and
returns =(values #f #t)= — the obarray is never modified and =st= is
ignored entirely. =unintern= is therefore a no-op that always returns nil.
Compare every sibling (=eval-set=, =eval-intern=, =env-dynstack-update=)
which correctly threads =st=. You probably intended (also converting the
symbol to a string, as =eval-intern= does):

#+begin_src scheme
(define (eval-unintern st name)
  (update&view
   (lambda (obj) (if (not obj) (values #f #f) (values #f #t)))
   st
   (=>env-obarray-key! (ensure-string name))
   ))
#+end_src

Note: the =defalias=/=defvaralias= tests happen to pass /because/
=unintern= is a no-op (their expected results assume =abcd= survives the
=(unintern 'abcd)= call). Those expected results would need re-checking
once =unintern= actually removes the symbol.

** elisp-eval.sld — =let= with a valueless binding passes a symbol to =new-symbol= (lines 1777, 1787)

#+begin_src scheme
((sym) (loop more (cons (new-symbol sym '()) bound) (+ 1 size)))
...
((? symbol? sym)
 (loop more (cons (new-symbol sym '()) bound) (+ 1 size)))
#+end_src

You wrote =(new-symbol sym '())=, which is wrong because in these two
match clauses =sym= is a raw Scheme symbol (from the parsed binding form),
but =new-symbol= requires its =name= to be a string and raises =(error
"not a string" name)= otherwise. The adjacent =(sym expr)= clause on
line 1781 correctly uses =(new-symbol (ensure-string sym) result)=, so
this is an inconsistency: =(let ((x)) ...)= and =(let (x) ...)= both throw,
even though these are valid in Emacs (they bind =x= to nil). You probably
intended:

#+begin_src scheme
((sym) (loop more (cons (new-symbol (ensure-string sym) '()) bound) (+ 1 size)))
...
((? symbol? sym)
 (loop more (cons (new-symbol (ensure-string sym) '()) bound) (+ 1 size)))
#+end_src

(=let*= is unaffected because it uses =elstkfrm-sym-intern!=, which
=ensure-string=s internally.) Not caught by the tests because every
tested =let= binding supplies a value.

** environment.sld — =change-var-to-dynamic= creates a bogus binding when the var is not lexically bound (line 1251)

#+begin_src scheme
(let loop ((lexstk (env-lexstack st)))
  (cond
   ((null? lexstk) (intern name))
   ...
   (else ... (intern sym))))
#+end_src

where

#+begin_src scheme
(define (intern sym)
  (let*((sym (or sym (new-symbol name))) ...) ...))
#+end_src

You wrote =(intern name)= for the "variable not found in the lexical
stack" case, which is wrong because =intern='s first line is =(or sym
(new-symbol name))=: passing the string =name= (always truthy) prevents
=(new-symbol name)= from ever running, so the raw *string* gets stored as
the dynamic-stack value instead of a =<sym-type>= object. Every other
caller passes an actual symbol object. You probably intended =(intern #f)=
so a fresh symbol is created:

#+begin_src scheme
((null? lexstk) (intern #f))
#+end_src

This is the single-argument =defvar= path (=eval-dynamic-defvar= ->
=change-var-to-dynamic=) for a variable that was never let-bound; not
exercised by the current tests.

** elisp-eval.sld — =get= looks up the property under the wrong key type (line 2284)

#+begin_src scheme
(define (eval-get st sym prop)
  (view-on-symbol
   st sym
   (lambda (obj)
     (view obj (=>sym-plist! (ensure-string sym)) (=>hash-key! prop)))))
#+end_src

You wrote =(=>hash-key! prop)= with =prop= left as-is, which is wrong
because =put= (=eval-put=, line 2288) and =setplist= (=plist-to-dict=)
both store plist entries under *string* keys (=(ensure-string prop)= /
=symbol->string=), so a property written with =(put 'x 'k v)= is stored
under ="k"= but read back by =(get 'x 'k)= under the symbol ='k=. Since the
plist hash table compares with =equal?=, the string and symbol keys never
match and =get= returns nil for anything =put= stored. You probably
intended to mirror =eval-put=:

#+begin_src scheme
(define (eval-get st sym prop)
  (let ((prop (ensure-string prop)))
    (view-on-symbol
     st sym
     (lambda (obj)
       (view obj (=>sym-plist! (ensure-string sym)) (=>hash-key! prop))))))
#+end_src

(The internal call =(eval-get st sym "defalias-fset-function")= in
=eval-defalias= works only because it already passes a string.) Not caught
because there is no =get=/=put= round-trip test.

** elisp-eval.sld — =i-%elisp-apply= shadows the call arguments in the raw =(lambda …)= function-cell case (lines 978-983)

#+begin_src scheme
(lambda (head arg-exprs loc)          ; <- arg-exprs = the actual call arguments
  ...
  ((pair? func)
   (match func
     (('lambda arg-exprs body ...)    ; <- rebinds arg-exprs to the formal parameter list!
      (let ((func (apply (syntax-eval elisp-lambda) func)))
        ((interpret-new-frame interp)
         (defun-make-lambda 'lambda (%unpack arg-exprs) body)
         ((interpret-args interp) arg-exprs))))   ; <- evaluates the *formals*, not the call args
     ...)))
#+end_src

You wrote the match pattern =('lambda arg-exprs body ...)=, which is wrong
because =arg-exprs= is already bound (by the enclosing =lambda=) to the
actual call arguments; the pattern shadows it with the lambda's *formal
parameter list*, so =((interpret-args interp) arg-exprs)= then evaluates
the formal parameter names as argument expressions (typically producing
"void variable"), instead of evaluating the real call arguments. Note the
sibling =('macro . func)= clause just below correctly leaves =arg-exprs=
referring to the outer (call-argument) binding. You probably intended to
rename the match variable and pass the outer =arg-exprs=:

#+begin_src scheme
(('lambda formals body ...)
 ((interpret-new-frame interp)
  (defun-make-lambda 'lambda (%unpack formals) body)
  ((interpret-args interp) arg-exprs)))
#+end_src

(The =(let ((func (apply (syntax-eval elisp-lambda) func)))= binding is
also dead here — the result is never used.) This path is reached when a
symbol's *function cell* holds a raw =(lambda …)= list (e.g. after =(fset
'f '(lambda (x) x))=) and =f= is then called by name; not exercised by the
tests, which reach lambda lists only through =apply=/=funcall= (which
convert via =eval-function-ref= first).

** elisp-eval.sld — =fmakunbound= does not clear the function cell (lines 2359-2361)

#+begin_src scheme
(define (eval-fmakunbound st sym)
  (view-on-symbol st sym (lambda (obj) (view st (=>env-obarray-key! sym)))))
#+end_src

You wrote a body that only *views* the obarray entry, which is wrong
because =fmakunbound= is supposed to *remove* the symbol's function
binding — this version mutates nothing, so the function stays bound.
(It also passes the raw symbol =sym= to =(=>env-obarray-key! sym)=, whose
underlying hash uses =string=?=/=string-hash= and would choke on a
non-string.) Compare =eval-makunbound=, which clears the value slot. You
probably intended something like:

#+begin_src scheme
(define (eval-fmakunbound st sym)
  (update-on-symbol
   st sym
   (lambda (obj) (values (lens-set #f obj (=>sym-function! (ensure-string sym))) obj))))
#+end_src

Not exercised by the tests.

** environment.sld — =stack-update!= re-inserts the old symbol instead of the updated one (line 596)

#+begin_src scheme
(let-values (((updated-sym return) (updater sym)))
  (unless (eq? sym updated-sym)
    (hash-table-delete! hash (sym-name sym))
    (hash-table-set! hash name sym))   ; <- stores `sym`, not `updated-sym`
  (values whole-stack (list return)))
#+end_src

You wrote =(hash-table-set! hash name sym)=, which is wrong because this
branch only runs when the updater returned a *different* object
(=updated-sym=); re-inserting the old =sym= discards the update. You
probably intended =(hash-table-set! hash name updated-sym)=. Latent: with
the record-mutating =>sym-value*!= lens the updater returns the same object
(so =eq?= holds and the branch is skipped), and the reachable callers
(=setq= via ==>stack!=, =change-var-to-dynamic=) currently never return a
fresh object here.

** elisp-eval.sld — =nconc= cycle detection accumulator is built backwards (line 2694)

#+begin_src scheme
(let find-end ((back '()) (this head) (next (cdr head)))
  (cond
   ((memq this back) (eval-error "list contains a loop" head))
   ...
   (else (find-end (cons back this) next (cdr next)))))
#+end_src

You wrote =(cons back this)=, which is wrong because =back= is meant to be
the list of already-visited cells that =(memq this back)= scans; consing
the accumulator into the =car= position produces a malformed structure
whose =cdr= is the input list itself, so =memq= never reliably finds a
revisited cell (and on a genuinely circular argument it loops forever
instead of raising "list contains a loop"). You probably intended =(cons
this back)=. Edge case (only matters for cyclic input); normal =nconc=
works.

** environment.sld — =print-stack-frame= numbers frames with descending negative indices (lines 1034-1043)

#+begin_src scheme
(define (print-stack-frame st)
  (let ((len (length (env-trace st))))          ; <- len computed but unused
    (let loop ((trace (reverse (env-trace st))) (i 0))
      (cond
       ((null? trace) #f)
       (else
        (let ((tr (car trace)))
          (print i ": " ... (line-break))
          (loop (cdr trace) (- i 1))))))))       ; <- 0, -1, -2, ...
#+end_src

You wrote =(loop (cdr trace) (- i 1))= starting from =i = 0=, which is
wrong because it prints frame numbers =0, -1, -2, …=; and =len= is computed
but never used. You probably intended =(+ i 1)= (or to start =i= at =(-
len 1)= and count down). Debug/diagnostic output only.

** environment.sld — =write-elisp-stack-trace= writes padding/space to the wrong port (lines ~817, 822)

#+begin_src scheme
(when (> nspaces 0)
  (write-string (vector-ref spaces nspaces)))   ; <- no `port`
(write-string (number->string i) port)
(write-char #\space)                            ; <- no `port`
(write-stack-trace-frame (vector-ref vec i) port)
#+end_src

You wrote =(write-string (vector-ref spaces nspaces))= and =(write-char
#\space)= without a =port= argument, which is wrong because everything else
in this loop writes to the passed =port=; these two default to
=current-output-port=, so the leading padding and the digit/frame
separating space go to a different port whenever =port= is not the current
output port. You probably intended to pass =port= to both. Cosmetic.

* Notes on Emacs-Lisp fidelity (not necessarily bugs)

- =dotimes= (elisp-eval.sld ~1638): the spec is bound as =(var limit-expr
  final-exprs ...)= and accepts *multiple* result forms, whereas Emacs
  =dotimes= takes at most one =RESULT= form =(VAR COUNT [RESULT])=. Also,
  during the result form Emacs binds =var= to =COUNT=; here the loop
  variable retains =limit-1=. Harmless for the tested cases.
- =eval= with an alist =LEXICAL= argument (=%elisp-eval=, ~463): the alist
  is pushed on the *dynamic* stack (mode =#f=) and =lexical-binding=
  evaluates to =#f=. This matches the test expectation =(#f 3)=, but real
  Emacs treats the alist as the lexical environment. Appears intentional.
- =set-lexical-binding= / =env-push-new-elstkfrm!= already carry a FIXME
  about the =lexical-binding= obarray variable; setting it to =#f= through
  =(=>env-obarray-key! …)= deletes the key (because =>hash-key*!= deletes
  on =#f=), which can transiently make =lexical-binding= a void variable in
  dynamic top-level evaluation. Flagging only because it corroborates the
  existing FIXME.
