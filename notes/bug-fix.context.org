I think we now have a concrete Schemacs-side trigger for the Guile crash.

%elisp-form-gather-symbols receives an equality choice but ignores it:

```scheme
(define (%elisp-form-gather-symbols o equal? sym->str)
  ...
  (make-hash-table)
  ...)
```

During function construction, elisp-eval.sld:2157 requests a string-keyed table:

```scheme
(elisp-form-gather-symbols
 form
 string=?
 symbol->string)
```

Before the port, the lexically bound `equal?` parameter was passed to `make-hash-table`, so this created a `string=?` table. After the port it creates a default-comparator table instead.

The trace supports this: the crash happens while processing another `defun`, and captured lexical environments print with:

```text
equivalence-function: #<procedure default-equality (a b)>
```

They should use `string=?`. This explains why basic comparator tests pass but repeated function definitions eventually destabilize Guile.

I recommend changing this internal path to accept a comparator:

```scheme
(define (%elisp-form-gather-symbols o comparator sym->str)
  ((elisp-form-fold ...)
   (make-hash-table comparator)
   o))
```

Then:

```scheme
;; Default entry point
(%elisp-form-gather-symbols
 o
 (make-eq-comparator)
 (lambda (sym) sym))
```

and at elisp-eval.sld:2157:

```scheme
(elisp-form-gather-symbols
 form
 (make-string-comparator)
 symbol->string)
```

Because `elisp-form-gather-symbols` is exported, we should decide whether its optional argument officially changes from an equality predicate to a comparator. Alternatively, a small compatibility conversion can recognize `eq?`, `eqv?`, `equal?`, and `string=?`.

Before implementing that fix, I would add and commit:

1. A parser test proving that the requested equality/comparator is used.
2. A Guile integration regression that loads `byte-run.el`; it currently exits with signal 11.
3. Ideally, a smaller regression that evaluates the sequence of top-level forms through the definition at `byte-run.el:674`.

There are also two independent arity bugs to address afterward:

- elisp-eval.sld:2714 returns `equal?`, which line 2728 then calls with zero arguments. It should return `make-equal-comparator`.
- comparator.sld:126 creates a two-argument unavailable-hash procedure, but comparator hashes are called with one argument.

Guile has known VM defects where ordinary arity/value errors become segfaults, including one fixed in 3.0.10 and another reported against 3.0.9: [Guile bug #50153](https://debbugs.gnu.org/db/50/50153.html), [Guile bug #68362](https://debbugs.gnu.org/db/68/68362.html). Your `/usr/local/bin/guile` reports version `UNKNOWN`, while Homebrew currently offers stable 3.0.11, so testing 3.0.11 remains worthwhile—but I would fix the ignored comparator first because it is a real regression regardless of Guile.
