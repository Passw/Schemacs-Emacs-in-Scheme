* Executive summary (please read first)

You told me "all of the code where the line and column numbers are tracked
seem to be incorrect ... almost none of the tests that involve counting
characters seem to be passing." After tracing every statistics test case by
hand, my conclusion is the opposite of what it looks like:

- The statistics *code* is, for non-empty buffers, *essentially correct*.
- Most of the failing =with-buffer-state-stats= assertions fail because the
  *expected* values hard-coded in =pretty-tests.scm= are miscalculated, not
  because the code is wrong. The proof is that test cases 1, 2, 5, 6, 7, 8
  pass, and their passing pins down the intended semantics (line lengths and
  char counts *include* the trailing newline that terminates a line); the
  failing cases 9, 10, 11 and =basic-test-case= were hand-computed with a
  *different* rule (excluding the newline, or adding the indent to the char
  count), so they disagree with both the code and the passing cases.
- There is exactly *one* genuine stats-code defect exposed by the tests: the
  initial/empty stats record has =#f= and =0= in the wrong fields (finding
  A1 below).

I give the corrected expected values in section B so you can verify this
independently. Separately, by inspection I found several *real* code bugs
that the current tests do not exercise (section A).

Because the passing cases are decisive, let me establish the semantics the
code actually implements (and that the passing tests confirm):

- A committed line's string *includes* the =\n= that terminated it
  (=buffered-line-break= writes the newline into the string port *before*
  =%buffered-flush= captures it). The final line, flushed at finalize, has
  no trailing =\n=.
- Blank lines are the =*empty-line*= singleton, string ="\n"=, counted by
  =numzeros=.
- =maxlen=/=minlen= are max / min-non-empty of =string-length= (newline
  included); =charcount= is the sum of =string-length= (newline included,
  indentation *not* included); =minindent=/=maxindent= range over line
  indents.

* A. Genuine code bugs

** [HIGH] A1 -- initial stats put =#f= / =0= in swapped fields

In =new-line-buffer-stats= (line 253) the zero-argument case is:

#+begin_src scheme
   (() (make<pp-line-buffer-stats-type> 0 0 0 0 #f #f))
#+end_src

The field order is =(maxlen minlen numzeros charcount minindent maxindent)=,
so this sets =maxlen=0 minlen=0 minindent=#f maxindent=#f=. That is
backwards: for a buffer with no lines the maximum/minimum line *length* is
undefined (should be =#f=), while the indentation floor is naturally =0=.
The empty-buffer tests confirm this -- they expect
=#<... maxlen: #f minlen: #f ... minindent: 0 maxindent: 0>= but the code
returns =maxlen: 0 minlen: 0 ... minindent: #f maxindent: #f=, i.e. exactly
this record with the two pairs swapped.

You probably intended:

#+begin_src scheme
   (() (make<pp-line-buffer-stats-type> #f #f 0 0 0 0))
#+end_src

*Caveat -- this fix is coupled to A2.* The =max-len= / =min-len= update
lambdas cannot currently start from =#f= (see A2), so they must be fixed
together, otherwise the first line pushed will evaluate =(max #f n)= and
raise a type error.

** [HIGH] A2 -- =max-len= / =min-len= updates cannot tolerate the =#f= sentinel

In =pp-update-stats-line!= (lines 470-480):

#+begin_src scheme
   (update (lambda (len) (max len (string-length str)))
    stats =>pp-line-buffer-max-len)
   ...
   (update (lambda (len) (if (> len 0) (min len strlen) strlen))
    stats =>pp-line-buffer-min-len)
#+end_src

These assume =len= is a number: =(max #f n)= and =(> #f 0)= both error. This
is why the code is *forced* to initialise =maxlen=/=minlen= to =0= rather
than =#f= -- which then produces the wrong empty-buffer result (A1). By
contrast, the indent updates on lines 482-483 are written defensively:

#+begin_src scheme
   (lambda (count) (if (not count) indent (compare indent count)))
#+end_src

You probably intended the length updates to guard the sentinel the same way,
e.g. =(lambda (len) (if len (max len strlen) strlen))= for max-len and
=(lambda (len) (if len (min len strlen) strlen))= for min-len. With that in
place, the =(> len 0)= special-case in min-len is also unnecessary. (Note
the indent updates and the length updates disagree today about which
sentinel they expect, =#f= vs numeric =0=; A1 makes them consistent.)

** [HIGH] A3 -- =new-line-buffer= tests =pp-line-buffer-type?= where it means =mutable-vector-type?=

The backing store field of =<pp-line-buffer-type>= is documented as "a
=<MUTABLE-VECTOR-TYPE>=", and =new-mutable-vector= is used to build it. But
the guards that are supposed to accept a *pre-allocated backing vector*
check the wrong predicate. In the 1-argument case (line 346):

#+begin_src scheme
   ((pp-line-buffer-type? init) (new-line-buffer #f init))
#+end_src

and in the 2-argument =sink= dispatch (line 363):

#+begin_src scheme
   ((pp-line-buffer-type? sink) sink)
#+end_src

which is wrong because a =<mutable-vector-type>= (the value the docstring
tells callers to pass) is *not* a =pp-line-buffer-type?=, so it falls through
to the =else= and raises "second argument must be an integer buffer size, or
a line buffer". Meanwhile a =pp-line-buffer-type?= would be stored verbatim
into the =buffer= field, nesting a whole line-buffer where a mutable vector
is expected. The tell-tale sign: =mutable-vector-type?= is imported (line 46)
but never referenced anywhere in the library. You probably intended:

#+begin_src scheme
   ((mutable-vector-type? init) (new-line-buffer #f init))   ; line 346
   ...
   ((mutable-vector-type? sink) sink)                        ; line 363
#+end_src

** [MEDIUM] A4 -- =pretty='s =else= branch forgets to call =error=

In =pretty= (line 997):

#+begin_src scheme
   (else "incorrect type for first argument" sink)
#+end_src

which is wrong because this is a two-expression =else= that simply evaluates
the string, then =sink=, and returns =sink= as the "state" =pp=. The invalid
argument is then handed to =%run-pp= / =%finalize=, producing a confusing
downstream failure instead of a clear diagnostic. You probably intended:

#+begin_src scheme
   (else (error "incorrect type for first argument" sink))
#+end_src

** [LOW] A5 -- duplicated =cond= clause in =pretty=

Lines 992-993 are identical:

#+begin_src scheme
   ((pp-line-buffer-type? sink) (print-to-buffer #f sink))
   ((pp-line-buffer-type? sink) (print-to-buffer #f sink))
#+end_src

The second is dead code. Harmless, but almost certainly one of them was
meant to be a different predicate (e.g. =output-port?= is already handled
above; possibly =pp-state-type?= or =mutable-vector-type?= was intended).

** [MEDIUM] A6 -- printing a literal =#\newline= char emits the newline twice

In =%print='s character branch (lines 786-792):

#+begin_src scheme
   ((char? arg)
    (lambda ()
      (%check-indent pp)
      (write-char arg (pp-state-output-port pp))
      (when (char=? arg #\newline)
        (%line-break pp))))
#+end_src

which is wrong because for =arg = #\newline= it first =write-char='s the
newline into the current line's string port, and *then* =%line-break= (via
=buffered-line-break= / =immediate-line-break=) writes *another* newline. So
a lone =#\newline= produces two line breaks (an extra blank line). Compare
the string branch (lines 762-766), which on a =#\newline= calls
=%line-break= and does *not* =write-char= it. You probably intended the char
branch to mirror the string branch:

#+begin_src scheme
   ((char? arg)
    (lambda ()
      (cond
       ((char=? arg #\newline) (%line-break pp))
       (else
        (%check-indent pp)
        (write-char arg (pp-state-output-port pp))))))
#+end_src

(This is currently untested -- no test case prints a bare =#\newline= char --
which is why it has gone unnoticed.)

** [MEDIUM] A7 -- the two char-count code paths disagree (indent in / indent out, and one skips most stats)

=pp-update-stats-line!= counts characters *without* indentation (line 481):

#+begin_src scheme
   (update (lambda (count) (+ count strlen)) stats =>pp-line-buffer-char-count)
#+end_src

but =buffered-write-line='s port branch counts them *with* indentation and
updates *only* the char count, skipping maxlen/minlen/numzeros/indent
entirely (lines 583-589):

#+begin_src scheme
   (when stats
     (update
      (lambda count
        (apply + (pp-line-indent line) (string-length (pp-line-string line)) count))
      stats =>pp-line-buffer-char-count))
#+end_src

which is wrong because whether a character count includes indentation now
depends on which path a line took (normal flush vs. a =<pp-line-type>=
printed into an already-open line), and a line written through this branch
silently fails to contribute to the length/zero/indent statistics. You
probably intended both paths to funnel through =pp-update-stats-line!= (and
to agree on the indent question). Deciding whether =charcount= should include
indentation is your call, but it must be one rule -- see B, where the
inconsistent test expectations trace back to exactly this ambiguity.

* B. Test-expectation errors in pretty-tests.scm (code is correct here)

These assertions fail, but the *code's* output is the correct one; the
hard-coded =expected= stats are miscalculated. Values shown as
=(maxlen minlen numzeros charcount minindent maxindent)=.

** =basic-test-case= (line 196)

Buffer lines (string, newline included): =(0,"--- hello ---\n")=14,
=(4,"hello\n")=6, =(0,"\n")=empty, =(0,"\n")=empty, =(4,"hello")=5.

- Written expected: =(14 0 5 27 0 4)=
- Correct value:    =(14 5 2 27 0 4)=

=minlen= is 5 (shortest non-empty line "hello"), not 0; =numzeros= is 2 (two
blank lines), not 5. The code returns =(14 5 2 27 0 4)=.

** Advanced case 9: =(repeat 3 "Hello" #\? (line-break))= (line 166)

Three lines ="Hello?\n"= (7 chars each).

- Written expected: =(6 6 0 18 0 0)=
- Correct value:    =(7 7 0 21 0 0)=

The expected value excludes the terminating newline; but case 2
=(print "Hello" (line-break) "Hello")= expects =(6 5 0 11 0 0)= -- which
*includes* the newline in the first line's length (6 = ="Hello\n"=) and
passes. The two cannot both be right; case 9 is the miscalculated one.

** Advanced cases 10 & 11: the =indent-by 2= paragraphs (lines 170, 181)

Nine lines: =(2,"Hello\n")= x3, =(0,"Hello\n")= x1, =(0,"Hello")= x1, and
four blank =(0,"\n")= lines.

- Written expected: =(7 7 4 39 0 2)=
- Correct value:    =(6 5 4 33 0 2)=

Here the expected =charcount= (39) equals the length of the *port-mode*
string, i.e. it counts indentation spaces too; and =maxlen=/=minlen= (7)
appear to be =indent + text= with the newline dropped. Neither matches the
buffer-stats rule the code (and the passing cases) use. The code returns
=(6 5 4 33 0 2)=.

** Advanced cases 3 & 4: =(print #f)= and =(print #f #f)= (lines 147, 150)

- Written expected: =(#f #f 0 0 0 0)=
- Code returns:     =(0 0 0 0 #f #f)=

This is the *one* place the code is genuinely wrong -- see finding A1/A2. The
test expectation is the sensible one.

* C. Minor / cosmetic

- =%print= (line 748) comment claims it "has a recursion counter to prevent
  infinite recursion, pass 0 as the second argument", but =%print= takes only
  =(pp arg)= and callers pass two args; the comment is stale.
- =print= (lines 830-831) binds =old-indent=/=old-char= and never uses them;
  =indent-by= (lines 878-884) saves and restores =old-char= although it never
  changes the indent char. Dead code, harmless.
- =display-lines= (lines 140-147): the two-argument =cond= has no =else=, so a
  =write/port= that is neither a procedure nor an output port returns
  unspecified instead of erroring.
- =print-to-port= (lines 701-702) tests =(port? sink)= before
  =(output-port? sink)=; =port?= is also true for input ports, which would
  then fail on the first write. Prefer testing =output-port?= (input ports
  are not valid sinks).
- =repeat='s fast path for a single string/char argument (lines 854-856)
  writes with =display=/=write-char= directly, bypassing =%print='s
  =#\newline=->line-break translation. Repeating a string that contains
  newlines will therefore embed literal newlines inside one line's string
  rather than splitting it into buffer lines. Probably fine as an
  optimization, but worth a comment given A6.

* Priority summary

1. A1 + A2 (must be fixed together): empty/initial stats fields swapped, and
   the length updates need to tolerate the =#f= sentinel. This is the only
   stats defect the tests actually catch.
2. A3: =new-line-buffer= uses =pp-line-buffer-type?= where it means
   =mutable-vector-type?= (imported but otherwise unused).
3. A4: =pretty='s =else= branch is missing its =error= call.
4. A6: literal =#\newline= char double-emits a newline.
5. A7: reconcile the two divergent char-count update paths.
6. Section B: fix the miscalculated =expected= values in =pretty-tests.scm=
   for =basic-test-case= and advanced cases 9, 10, 11 -- the library is
   producing the correct numbers for those.
