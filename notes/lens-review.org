#+TITLE: Code Review: Lens Library (schemacs lens)
#+AUTHOR: Code review for Ramin Honary
#+DATE: 2026-07-15

Files reviewed:

- =schemacs/lens.sld=
- =schemacs/lens-tests.scm=

Brief: typos, inconsistent variable use (relative offset vs. absolute
index, value vs. procedure, etc.), off-by-one and arithmetic errors, logic
errors, accidental infinite recursion, wrong number/type of arguments. No
code was edited.

* Executive summary

The heavily-exercised core (=view=, =update&view=, =lens-set=, =compose=,
=record-unit-lens=, =>car/=>cdr/=>head, hash and find/bring/assoc lenses on
the paths the tests hit) checks out. As you predicted, the bugs cluster in
the corners that the test suite never reaches: I confirmed that =lens-set!=,
=unit-lens-swap=, =lens-swap!=, and =get-rule-declaration/index->lens= have
*zero* occurrences in =lens-tests.scm=, and the failing behaviours below all
live on exactly those un-hardened paths.

Findings are ordered by severity. Line numbers refer to =lens.sld= unless
noted.

* A. Bugs

** [HIGH] A1 -- =>vector-index! grows the backing vector to the wrong size

In the updater of =>vector-index! (line 996), when the index =i= is past the
end of an existing vector:

#+begin_src scheme
   ((>= i len)
    (let ((new-vec ((*default-vector-constructor*) (+ 1 len))))
      ((*default-vector-copier*) new-vec 0 vec)
      (let-values (((elem result) (updater #f)))
        (vector-set! new-vec i elem)
        (values new-vec result))))
#+end_src

which is wrong because =*default-vector-constructor*= takes an *index* and
returns a vector large enough to hold that index (its default is
=(lambda (i) (make-vector (+ 1 i)))=). You pass it =(+ 1 len)=, producing a
vector of size =len+2= that can only index up to =len+1= -- but the element
you then store is at index =i=, which may be far larger. So
=(vector-set! new-vec i elem)= is out of bounds whenever =i >= len+2=.

Concretely: =(lens-set 'x (vector 1 2) (=>vector-index! 10))= builds a size-4
vector and then does =(vector-set! v 10 'x)= -> error.

You probably intended to size the new vector for the target index =i=:

#+begin_src scheme
   (let ((new-vec ((*default-vector-constructor*) i)))
#+end_src

(The tests only ever grow by one slot at a time -- =(=>vector-index! 2)= on a
freshly-created length-3 vector -- so =i = len-1= and this path is never
stressed.)

** [HIGH] A2 -- =lookup-listbox= does =(cdr '())= on a miss

=lookup-listbox= (lines 1606-1609):

#+begin_src scheme
   (lambda (rec)
     (let*((found (view (listbox) (=>find (lambda (item) ((car item) rec))))))
       (if found (cdr found) #f)))
#+end_src

which is wrong because =(view ... (=>find ...))= returns ='()= (not =#f=)
when nothing matches, and ='()= is truthy in Scheme, so the =(if found ...)=
test succeeds and =(cdr '())= raises a wrong-type error instead of returning
=#f=. This is reached through =get-rule-declaration/index->lens= /
=apply-typed-lens= whenever an integer/string/symbol index is used on a
record type that has *no* declared rule -- e.g. =(view some-list 0)= (a list
is not a vector, so it falls through to the rule lookup, finds nothing, and
errors on =(cdr '())= rather than reporting "cannot index record by value of
type"). You probably intended:

#+begin_src scheme
   (if (pair? found) (cdr found) #f)
#+end_src

** [HIGH] A3 -- =lens-set!= always returns =#f=, never =new-info=

=compound-lens-set!= (line 611), which backs the exported =lens-set!=:

#+begin_src scheme
   (let-values
       (((_rec return)
         (compound-update (lambda (_) (values new-info #f)) record-in-focus lenses)))
     return)
#+end_src

which is wrong because it returns =return=, the second value threaded up from
the updater -- and that second value is the literal =#f= you supplied in
=(values new-info #f)=. So =lens-set!= returns =#f= for every call, whereas
its docstring promises it "returns =NEW-INFO=". Compare =compound-swap!=
(line 633), which is correct precisely because its updater puts the value it
wants returned (=old-info=) in the second slot. You probably intended the
second value to carry =new-info=:

#+begin_src scheme
   (compound-update (lambda (_) (values new-info new-info)) record-in-focus lenses)
#+end_src

** [MEDIUM-HIGH] A4 -- =default-unit-lens-setter= passes a 1-value thunk where 2 values are required

=default-unit-lens-setter= (lines 299-310):

#+begin_src scheme
   (lambda (record-in-focus new-info)
     (let-values
         (((record-in-focus _return)
           (updater (lambda _ new-info) record-in-focus)))
       record-in-focus))
#+end_src

which is wrong because =updater= is a unit-lens updater, and it calls the
inner function expecting *two* values (e.g. =default-unit-lens-updater= does
=(let-values (((new-info return) (updater (getter rec)))) ...)=). Here the
inner function is =(lambda _ new-info)=, which yields a *single* value, so
the enclosing =(((new-info return) ...))= raises "wrong number of values".
You probably intended:

#+begin_src scheme
   (updater (lambda _ (values new-info #f)) record-in-focus)
#+end_src

This is latent because =lens-set= / =update&view= drive lenses through the
*updater*, never the setter; the setter derived here is only invoked via the
(untested) =unit-lens-set= / =unit-lens-swap= on a lens built from the
2-argument =unit-lens= (getter+updater) form -- e.g.
=(unit-lens-swap v vec (=>vector-index! i))= would trip it.

** [MEDIUM-HIGH] A5 -- =>assoc-by view and update disagree about the focus

In =>assoc-by (line 1174):

#+begin_src scheme
   (viewer (endo-view =>ulens))
   ...
   (setter  (lambda (rec val) (lens-set (cons key val) rec =>ulens)))
   (updater (lambda (up rec)
              (update&view
               (lambda (rec)
                 (let-values (((elem return) (up (if (null? rec) #f (cdr rec)))))
                   (values (if elem (cons key elem) '()) return)))
               rec =>ulens)))
#+end_src

which is wrong because the viewer returns the *whole* matched pair
=(key . value)= (=>ulens = =(=>find predicate)= focuses on the list element),
while the updater feeds =up= the =(cdr rec)= -- i.e. the *value* -- and the
setter takes a bare value. So =(view alist (=>assoc-by ... 'k))= returns
=(k . v)= but =(update&view f alist (=>assoc-by ... 'k))= applies =f= to =v=;
the lens focuses on two different things depending on the operation, and any
lens composed after it sees the pair on the view side and the value on the
update side. The docstring also says view "will return the =CDR= of the
pair." Notably =>guard (line 1223) does this correctly for its own lookup
with =(view rules (=>find (by rec)) =>cdr)=. You probably intended:

#+begin_src scheme
   (viewer (endo-view =>ulens =>cdr))
#+end_src

** [MEDIUM] A6 -- =>guard's "no guard to handle record" error is unreachable

In =>guard (lines 1222-1233):

#+begin_src scheme
   (let ((found (view rules (=>find (by rec)) =>cdr)))
     (cond
      ((not found) (error "no guard to handle record of given type" rec))
      (else
       (cond
        ((null? found) =>self)
        ((pair? found) (apply lens found))
        ...))))
#+end_src

which is wrong because when no guard matches, =(=>find (by rec))= yields
='()= and =>cdr of ='()= is ='()=, so =found= is ='()=, never =#f=. Thus
=(not found)= can never be true -- the "no guard to handle record" error is
dead code, and an unmatched record silently falls through =(null? found)= to
=>self (the identity lens), so e.g. =(lens-set v non-matching =>guard...)=
quietly replaces the whole record instead of erroring. You probably intended
=(null? found)= to trigger the error -- though note that also collides with
the legitimate "guard matched but has an empty lens list" case, so the
no-match and empty-lens cases need to be told apart (e.g. have =by= return a
sentinel, or check the =>find result before taking =>cdr).

** [LOW-MEDIUM] A7 -- =>vector-index! reads an uninitialised slot when building a fresh vector

In the same updater (lines 991-1004), the non-existent-vector case:

#+begin_src scheme
   (let*((vec (if (not vec) (make-vector (+ 1 i)) vec))
         (len (vector-length vec)))
     (cond
      ((>= i len) ...)
      (else
       (let-values (((elem result) (updater (vector-ref vec i))))
         ...))))
#+end_src

which is wrong in two small ways when =vec= was =#f=: (1) it uses raw
=make-vector= instead of =(*default-vector-constructor*)=, bypassing the
parameter the rest of the procedure honours; and (2) since the fresh vector
has size =i+1=, =i < len= holds and control reaches =(updater (vector-ref vec i))=,
reading the *uninitialised* slot =i= and handing that unspecified value to
=updater=. The resize branch is careful to pass =#f= to a brand-new slot
(=(updater #f)=); this branch should do the same. Harmless for =lens-set=
(its updater ignores the argument) but wrong for =update&view= updaters that
read the old value.

* B. Cosmetic / documentation

- =>head (line 908) is labelled ='=>car*= (copy-pasted from =>car); its
  =lens->expr= will therefore misidentify it. Should be ='=>head=.
- =>encapsulate (line 1393): =(error "=>encapsulate function argument ~a not a ..." lens)=
  passes a =~a= that =error= does not interpolate (it is not =format=); the
  lens still shows as an irritant, but the =~a= prints literally.
- =fail-if-incorrect-type= (line 1558): =(raise (error ...))= double-wraps --
  =error= already raises, so the surrounding =raise= is unreachable. (=>assert
  is neither exported nor used.)
- =cons-lens= / =>car docstring (line 880) claims the lens is canonical and
  reduces =(cons '() '())= to ='()= "after an update", but the setter never
  performs that reduction. Doc/behaviour mismatch, not a runtime fault.

* Priority summary

1. A1 -- =>vector-index! growth sizes the new vector for =len+1=, overflowing
   for any target index =>= len+2=; use the index =i=.
2. A2 -- =lookup-listbox= does =(cdr '())= on a miss; guard with =(pair? found)=.
3. A3 -- =lens-set!= returns =#f= instead of the promised =new-info=.
4. A4 -- =default-unit-lens-setter= hands a 1-value thunk to a 2-value updater
   contract (latent: only via =unit-lens-set= / =unit-lens-swap=).
5. A5 -- =>assoc-by view returns the pair while update/set focus on the value.
6. A6 -- =>guard's no-match error is dead code; unmatched records silently
   become =>self.
7. A7 -- =>vector-index! feeds an uninitialised slot to the updater when
   materialising a fresh vector.
