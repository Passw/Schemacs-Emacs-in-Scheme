#+TITLE: Code Review — Schemacs UI framework
#+SUBTITLE: (schemacs ui) and (schemacs ui platform guile-gi-gtk3)
#+DATE: 2026-07-14
#+OPTIONS: toc:2 num:t

* Scope and method

This review covers the two files requested:

- =schemacs/ui.sld= — the platform-agnostic "virtual DOM" (~2830 lines).
- =schemacs/ui/platform/guile-gi-gtk3.sld= — the Gtk+ v3 reference
  back-end (~1670 lines).

The four failure classes you asked me to hunt for are used as the
top-level organization:

1. Wrong-type arguments.
2. Accidental infinite recursion / unbounded loops.
3. Stale references / incorrect results from aliasing.
4. Virtual-DOM updates that fail to trigger a redraw/recompute.

Then a section of additional correctness issues (unbound variables,
typos that will raise at runtime) and lower-priority observations.

Each finding is tagged with a rough *severity* (CRITICAL / HIGH /
MEDIUM / LOW) and a note on whether the buggy path is currently
*reachable* or *latent/dead* given the present call graph. Severity
assumes the path is or will become reachable.

I confirmed reachability with a repo-wide grep where it mattered
(e.g. =div-delete= → =div-pack-delete= → =for-each-div-pack= is live;
=diff-div= has no callers outside its own cluster).

* 1. Wrong-type arguments

** [CRITICAL] =state-var= passes constructor arguments in the wrong order (ui.sld 531–546)

Both two-argument branches of =state-var= swap =label= and
=equality-test= when they delegate to the three-argument form
=(label equality-test init-value)=:

#+begin_src scheme
((or (symbol? lbl/eq) (string? lbl/eq) (integer? lbl/eq))
 (state-var equal? lbl/eq init-value)   ; label=equal?, test=<the label symbol>
 )
((procedure? lbl/eq)
 (state-var lbl/eq equal? init-value)   ; label=<the predicate>, test=equal?
 )
#+end_src

Consequences:

- =(state-var 'my-label 42)= — the intended /label/ =\'my-label=
  becomes the =equality-test= field, because
  =(or equality-test equal?)= = =(or 'my-label equal?)= = ='my-label=.
  The =value= field is =42=. Now on the first update,
  =%update-var= evaluates ~((state-var-equality-test var) old new)~
  (line 337), i.e. it *applies the symbol ='my-label= as a
  procedure* → runtime "wrong type to apply" error. So a labelled
  state variable crashes the first time it is updated.

- =(state-var my-eq-proc init)= — the predicate is stored as the
  /label/, and =equal?= is used as the test, so a caller-supplied
  equality predicate is silently ignored.

*Fix:* swap the arguments so =label= comes first:

#+begin_src scheme
((or (symbol? lbl/eq) (string? lbl/eq) (integer? lbl/eq))
 (state-var lbl/eq equal? init-value))
((procedure? lbl/eq)
 (state-var #f lbl/eq init-value))
#+end_src

** [HIGH] =gtk-draw-pack-flow= applies =div-pack-subdiv-sizes= to a =<div-type>= (gtk3 1148)

#+begin_src scheme
(counter (vector-length (div-pack-subdiv-sizes o)))
#+end_src

=o= here is the =<div-type>= record, but =div-pack-subdiv-sizes= is
the raw field accessor of =<div-pack-type>= (ui.sld 1972), so this
raises a wrong-type record-accessor error. The sizes vector is already
in scope as =sizes=; use =(vector-length sizes)=.

(Note this whole procedure is currently gated behind the =flags=
branch that itself does not run — see §5 finding on the unbound
=flags= — but the bug is real once that branch is fixed.)

** [MEDIUM] =gtk-make-scroller= is given a boolean where it expects an orientation symbol (gtk3 1284, 1332)

=gtk-make-scroller o orient= only uses =orient= to expand a
=scrollbar:= property value of =#t= into ='horizontal= / ='vertical=.
Two call sites pass a non-orientation value:

- =gtk-draw-div-space= (line 1284): ~(gtk-make-scroller o #t)~ — passes
  the boolean =#t=.
- =gtk-draw-div-grid= (line 1332):
  ~(gtk-make-scroller o (div-prop-lookup 'scrolled: o))~ — passes the
  value of the =scrolled:= property (a boolean), not an orientation.

When the widget's =scrollbar:= property is =#t=, =orient= fails every
=eq?= test, =scrollprop= stays =#t=, and control falls through to
~(else (error "unknown value for 'scrollbar: property" #t))~. So a
grid/space with =scrollbar: #t= errors instead of scrolling. Pass a
real orientation symbol (e.g. the container's =div-pack-orientation=,
or ='both=/='vertical= as appropriate).

** [MEDIUM] =gtk-div-update-string= assumes =div-widget= is a raw =GtkLabel= (gtk3 212–225)

#+begin_src scheme
(wref (view old =>div-widget*!))
...
(label:set-text wref (div-content new))
#+end_src

For any label drawn through =gtk-draw-content=, the =div-widget= slot
holds a =<gtk-div-boxed-type>= (line 695), not the =GtkLabel=. Calling
=label:set-text= on the boxed wrapper is a type error. You'd need
=(gtk-div-boxed-content wref)= (and to handle the no-box case).

Mitigating fact: =gtk-div-update-string= is never installed as an
=on-update= handler anywhere except inside itself, so it is currently
*dead code* (see §4). If you revive it as the label fast-path, fix the
widget extraction first.

** [LOW] =gtk-set-cursor-index= / =gtk-move-cursor-index= write a read-only property (gtk3 1492–1499)

#+begin_src scheme
(text-buffer:cursor-position buffer index)   ; used as a setter
#+end_src

In Gtk+3 =GtkTextBuffer:cursor-position= is a *read-only* property;
the cursor is moved with =gtk_text_buffer_place_cursor= applied to an
iterator (as =gtk-set-cursor-position= at line 1501 correctly does).
Setting the property will either no-op or raise depending on how
guile-gi marshals a read-only property write. Route index-based cursor
moves through =get-iter-at-offset= + =place-cursor=.

* 2. Accidental infinite recursion / unbounded loops

** [HIGH] =for-each-div-pack= has no bounds check — runs off the end of the vector (ui.sld 2184–2196)

#+begin_src scheme
(define (for-each-div-pack proc)
  (lambda (pack)
    (let ((elems (div-pack-subdivs pack))
          (sizes (div-pack-subdiv-sizes pack)))
      (cond
       ((vector? elems)
        (let loop ((i 0))
          (proc (vector-ref elems i) i (vector-ref sizes i))
          (loop (+ 1 i))                 ; <- never terminates on its own
          ))
       (else (values))))))
#+end_src

The loop never tests =i= against =(vector-length elems)=; it recurses
forever and =vector-ref= raises "index out of range" the moment =i=
reaches the length. Compare the correct =for-each-div-grid= (line
1846) which guards with =(< i len)=.

This path is *live*: =div-delete= (exported) → =div-pack-delete= →
=for-each-div-pack=, so deleting any =div-pack= subtree crashes. It is
also reached through =for-each-div= (line 1329). *Fix:*

#+begin_src scheme
(let ((len (vector-length elems)))
  (let loop ((i 0))
    (when (< i len)
      (proc (vector-ref elems i) i (vector-ref sizes i))
      (loop (+ 1 i)))))
#+end_src

(Also consider guarding =sizes= length independently, as
=print-div-pack= does with =min=.)

** [MEDIUM] =%div-select= narrowing loop tests the wrong variable and references an unbound name (ui.sld 1226–1236)

#+begin_src scheme
(let ((o (let loop ((o div-in-focus))
           (cond
            ((floater-type? div-in-focus) (floater-div o))   ; tests div-in-focus, not o
            ((div-record-type? div-in-focus) o)              ; tests div-in-focus, not o
            ((use-vars-type? content)                        ; `content` is unbound here
             (loop (use-vars-value div-in-focus)))           ; recurses on div-in-focus, not o
            (else #f)))))
#+end_src

Three problems in one expression:

1. Every =cond= test inspects =div-in-focus= (the outer, fixed
   argument) instead of the loop variable =o=. The loop therefore
   never observes the narrowed value.
2. =content= is not bound in this scope. It happens to resolve to the
   top-level exported =content= /procedure/, so =(use-vars-type?
   content)= is always =#f= — which is the only thing that stops this
   from being an infinite loop when =div-in-focus= is a
   =use-vars-type=. That is, the code is "saved" from looping forever
   only by a second bug.
3. The recursion feeds =(use-vars-value div-in-focus)= rather than the
   narrowed =o=.

Net effect: =div-select= silently fails to descend through =use-vars=
nodes, and the intended fix (=(use-vars-type? o)= → =(loop
(use-vars-value o))=) would turn it into a genuine infinite loop
because the =floater/record= tests still look at =div-in-focus=.
Rewrite the whole =cond= to test and recurse on =o=.

** [LOW / latent] =%run-div-monad= — misplaced paren turns a =cond= clause into an always-raising application (ui.sld 164–180)

#+begin_src scheme
((div-monad-type? return)
 (when log-output ...)
 (div-resolve log-output return (%%run-div-monad log-output parent return))
 ((use-vars-type? return)                 ; NOT a cond clause — this is a call form
  (error "`use-vars` node resolved to another `use-vars` node" return 'from: o)))
#+end_src

The =((use-vars-type? return) (error ...))= form was clearly meant to
be a sibling =cond= clause, but it sits inside the body of the
=(div-monad-type? return)= clause. As written it is evaluated as a
function application: the argument =(error ...)= is evaluated first and
*always raises*. So any time a =use-vars= resolves to a =div-monad=,
this path throws the "resolved to another use-vars" error
unconditionally (and the =div-resolve= result just above is
discarded).

Currently *latent*: =apply-use-vars= (line 636–643) already runs any
returned monad before handing control back, so =return= is never a
=div-monad-type= at this point. But the code is a landmine if that
invariant changes. Restructure into a proper =cond=.

* 3. Stale references / aliasing producing incorrect results

** [MEDIUM] Duplicate/aliased widget references left in the =div= tree during pack drawing (gtk3 1040 vs 1071)

In =gtk-draw-pack-tiled-windows= the widget slot is written twice:

#+begin_src scheme
(lens-set split-wrefs o =>div-widget*!)   ; line 1040 — stores the raw vector
...
(lens-set wref o =>div-widget*!)          ; line 1071 — overwrites with the contain record
#+end_src

The first write leaves the =div-widget= transiently pointing at the
bare =split-wrefs= vector; it is only correct after the second write.
If any code observed the node between the two writes (e.g. a
size-allocate callback firing during =add1=/=add2=, which do realize
widgets) it would see the wrong widget type. Drop the first
=lens-set=; it serves no purpose.

** [MEDIUM] =gtk-div-updater= can pass a just-destroyed widget as the redraw target (gtk3 440–453)

#+begin_src scheme
(define (gtk-div-updater old new)
  (let*((old-wref (view old =>div-widget*!))
        (old-box  (gtk-get-outer-widget old-wref)))
    (gtk-delete-boxed-content old-wref)   ; may destroy old-box itself
    (gtk-draw-content new old-box)        ; …then draws into it
    (widget:show old-box)))
#+end_src

This is safe only because =from-var= divs are guaranteed a persistent
outer =GtkBox= (=gtk-prepare-outer-box=, line 420, returns the box only
when =div-from-var?=). If =old-wref= is ever a *raw* widget (no box) —
which is exactly what happens for non-=from-var= divs (line 697) —
then =gtk-get-outer-widget= returns that raw widget, =gtk-delete-boxed-content=
falls to its =else= branch and =gtk-unref-destroy=s it, and the
subsequent =gtk-draw-content=/=widget:show= operate on a destroyed
object. Today the dispatcher only ever updates =from-var= nodes so the
invariant holds, but it is fragile and undocumented. Consider asserting
that =old-wref= is a =gtk-div-boxed-type= (or =gtk-div-contain-type=)
before deleting.

** [LOW] =apply-use-vars= mutates =use-vars-value= before the updater sees the old value (ui.sld 624–653, 500–507)

=apply-use-vars= calls =(set!use-vars-value uses return)= internally
(line 644). =div-dispatch-updates= then also captures =old-value= /
=new-value= around it (lines 501–505). The ordering happens to work
because =old-value= is read *before* =apply-use-vars= runs, but the
value slot is written twice (once inside =apply-use-vars=, once after
=div-run-update=). It would be clearer and less fragile for
=apply-use-vars= not to write the slot, leaving the single write to the
dispatcher. Not a live bug, but an easy source of a future stale-value
regression.

* 4. Virtual-DOM updates that may not trigger a redraw

** [HIGH] 0- and 1-element =div-pack= nodes get no =on-update= handler → silent no-redraw (gtk3 979–1007)

In =gtk-draw-div-pack=, the =nelems = 0= and =nelems = 1= branches set
the =div-widget= but never install an =on-update= callback (only the
=else= branch reaches =gtk-draw-pack-*=, which set
=gtk-div-container-update=). The default updater that
=gtk-draw-content= installs (=gtk-div-updater=) is also skipped,
because =gtk-draw-content= dispatches pack content straight to
=gtk-draw-div-pack= and returns without touching =on-update=.

Result: when a =from-var= pack with 0 or 1 children changes,
=div-run-update= finds =(div-on-update old)= = =#f=, does nothing, and
returns the new node — so the state change is *swallowed with no
visible redraw*. Install =gtk-div-container-update= (and set the widget
to a =gtk-div-contain-type=) in these branches too.

** [HIGH] 0/1-element =div-pack= sets a container delete handler on a non-container widget (gtk3 1006)

Related to the above: after the =cond=,
=gtk-draw-div-pack= unconditionally runs

#+begin_src scheme
(lens-set gtk-div-contain-delete-all o =>div-on-delete*!)
#+end_src

but for 0/1 elements the =div-widget= is a bare =GtkBox= from
=gtk-empty-div=, not a =<gtk-div-contain-type>=.
=gtk-div-contain-delete-all= immediately calls
=(gtk-div-contain-outer wref)= on it → wrong-type record-accessor
error. So these packs cannot be deleted either. Give the small-arity
branches the same =<gtk-div-contain>= wrapping the general branch uses.

** [MEDIUM] The entire =diff-div= family is broken — and unused (ui.sld 1339–1379)

=diff-div-vector= will not diff anything even when wired up:

#+begin_src scheme
(let loop ((i old-len))          ; starts at old-len
  (cond
   ((< i old-len) (diff-div ...))  ; immediately false → body never runs
   (else (values))))              ; and there is no (loop (+ 1 i)) anyway
#+end_src

- =i= is initialized to =old-len=, so =(< i old-len)= is false on entry
  and no elements are compared.
- Even corrected to start at 0, the =(< i old-len)= branch never
  recurses, so it would compare only index 0.
- The outer =cond= has no =else=, so on a length mismatch or non-vector
  it returns unspecified instead of =new=.

Confirmed via grep that =diff-div= has *no callers* outside this
cluster (the live update path uses =div-run-update=, not =diff-div=).
So this is latent, but if you intend =diff-div= to become the
reconciliation engine, it needs: start at =0=, recurse with =(loop (+ 1
i))=, collect/return =new=, and an =else= that returns =new=
(or triggers a full replace) when shapes differ.

** [MEDIUM] Duplicated var in the update queue causes a subtree to be rebuilt multiple times (ui.sld 421–451, 481–507)

=%div-event-handler= collects every =update-var=/=signal-var= call into
=box= without de-duplication, and =div-dispatch-updates= is then run
once *per queued entry*. If a handler updates the same state var twice,
or a =use-vars= is subscribed to two vars that both changed, that
=use-vars= is re-applied and its Gtk subtree torn down and rebuilt
several times in one event. The final result is correct, but it is
wasted allocation/destruction of real GObjects (and extra
=gobject-ref=/=unref= churn, which your comment at gtk3 227–237 warns is
already delicate). De-duplicate =box= (and the union of subscribers)
before dispatching.

* 5. Other correctness bugs that will raise at runtime

These are plain typos / omissions that throw as soon as the line is
reached; grouped separately because they aren't subtle, but they will
bite.

** [HIGH] =floater-type?= is used but not imported into the Gtk back-end (gtk3 96, 273, 773)

The =(only (schemacs ui) …)= import block (lines 19–42) brings in
=floater=, =floater-div=, =floater-rect=, =for-each-floater= — but *not*
=floater-type?=. Yet =floater-type?= is called in =on-main-loop-start=
(96), =gtk-signal-focus!= (273), and =gtk-draw-app-window= (773). It is
exported by =(schemacs ui)= (ui.sld 130); it simply needs to be added to
the =only= list. As written this is an unbound-variable error on the
startup / focus / window-draw paths. (Verified by grep: no other import
provides it.)

** [HIGH] =gtk-draw-div-pack= references unbound =flags= (gtk3 997)

#+begin_src scheme
((eq? flags wrapping) ...)
#+end_src

There is no =flags= binding in this =let*= (bindings are =cont rect
from orient sizes subdivs nelems=). This should be
=(div-pack-flags cont)=. As written, the multi-element pack path raises
"unbound variable flags" before it can choose flow vs tiled vs nowrap.

** [HIGH] Typo =displau= in =gtk-draw-div-grid= (gtk3 1377)

#+begin_src scheme
(displau "; container:add grid ") (write grid) (newline)
#+end_src

=displau= is unbound; this fires whenever a grid has a scroller
(=scroll= truthy). Should be =display=.

** [MEDIUM] Unbound =box-ref= debug write in =gtk-draw-pack-nowrap= (gtk3 1254)

#+begin_src scheme
(display "; container:add box-ref ") (write box-ref) (newline)
#+end_src

The variable is =box-wref=, not =box-ref=. Reached when the nowrap pack
has a scroller. Fix the name (or drop the debug line).

** [MEDIUM] Unbound =old-index= in =gtk-index->line-column= (gtk3 1509–1519)

#+begin_src scheme
(text-buffer:cursor-position buffer old-index)   ; old-index never bound
(values line column)
#+end_src

=old-index= is not defined anywhere in the procedure. Besides being an
unbound reference, mutating the cursor as a side effect of a
*query* (index→line/column) is surprising — this line looks like a
leftover and can most likely just be deleted.

** [MEDIUM] =gtk-signal-focus!= error branch is a mis-written =cond= clause (gtk3 283–286)

#+begin_src scheme
(cond
 (wref (widget:grab-focus wref))
 (error "no widget reference" focus))
#+end_src

The second clause's *test* is the variable =error= (a procedure, hence
always truthy), and its *body* is the string then =focus=. So when
=wref= is =#f= this returns =focus= silently instead of raising. It
should be =(else (error "no widget reference" focus))=.

** [LOW] =parameterized-gtk-api= parameterizes =*impl/delete-from-cursor*= twice (gtk3 1573, 1576)

The same parameter is bound twice (to the same value). Harmless, but it
suggests a copy-paste slip — check whether one of them was meant to be a
different =*impl/…*= binding (e.g. =*impl/set-cursor-index*= vs
=*impl/get-cursor-index*=, or a missing =delete-range= companion).

** [LOW] =gtk-delete-from-cursor= range direction is ambiguous (gtk3 1527–1534)

=(gtk-buffer-range buffer cursor (- cursor to))= deletes between the
cursor and =cursor - to=. If =to= is a *count* this deletes backwards
(a backspace); if =to= is an *absolute offset* the sign is wrong. The
name =to= implies an absolute target. Worth pinning down against the
=(schemacs ui text-buffer)= contract and documenting.

* 6. Lower-priority observations (not bugs, but worth a look)

- *=check-state-vars= closes over the wrong list* (ui.sld 576–591): the
  local helper takes a =vars= parameter but its body reads
  =(car state-vars)= / =(cdr state-vars)= from the enclosing binding.
  It terminates (it walks =(cdr state-vars)= for the =null?= test) but
  only ever type-checks the *first* element, so a malformed list past
  index 0 passes validation. Also, =use-vars= given a single
  =state-var= (not a list) survives the guard via the
  =(state-var-type? state-vars)= check but then crashes in the
  subscription loop (line 604) which assumes a list. Decide whether a
  bare var is legal and normalize with =(if (state-var-type? x) (list
  x) x)=.

- *=gtk-draw-div-space= empty branch returns a widget, not a =div=*
  (gtk3 1279–1280): the =(not elems)= case returns the bare
  =gtk-empty-div= result, whereas every other =gtk-draw-*= returns the
  =div= node =o= (with =div-widget= set). Callers such as
  =gtk-draw-app-window= then store a raw widget where a =div= is
  expected, and =set! *gtk-top-level-div*= could hold a non-div. Make
  it set the widget on =o= and return =o=.

- *Redundant =gtk3-event-handler= nesting for key events* (gtk3 497–503,
  540): the key-press handler is wrapped in =gtk3-event-handler= by
  =gtk-set-event-handler=, and =gtk-key-press-event-handler= wraps the
  user callback in =gtk3-event-handler= again. That double-parameterizes
  the whole =*impl/…*= set per keystroke. Not incorrect, but avoidable
  overhead on the hot path.

- *=size->default= double-checks =expand=/=enclose=* (ui.sld 711–719):
  it tests both ='expand= and the variable =expand= (which /is/
  ='expand=), etc. Harmless redundancy.

- *Verify =rect2D= arity*: =ui.sld= constructs =rect2D= as
  =(rect2D point size)= (e.g. line 2284), while the Gtk back-end uses
  =(rect2D 0 0 1000 600)= (gtk3 776) and =(apply rect2D <4 ints>)=
  (gtk3 722). This only works if =rect2D= accepts both a
  =(point size)= form and an =(x y w h)= form. Worth confirming in
  =(schemacs ui rectangle)= — a mismatch here would be a wrong-type bug
  in the window-sizing path.

- *Unimplemented signals*: =*impl/signal-visible*=,
  =*impl/signal-enabled*=, =*impl/signal-properties*= are renamed on
  import (gtk3 46–48) but never bound in =parameterized-gtk-api=, so
  =signal-visible!= / =signal-enabled!= / =signal-properties!= raise the
  default "not implemented" error. Presumably intentional (TODO), noting
  it for completeness.

* Summary — suggested fix order

1. =state-var= argument order (§1) — corrupts state on the most common
   API call; crashes on first update.
2. =for-each-div-pack= bounds check (§2) — crashes on any =div-pack=
   delete/traversal.
3. =floater-type?= import, =flags= (gtk3 997), =displau=, =box-ref=,
   =old-index= (§5) — hard unbound-variable/typo errors on live paths.
4. 0/1-element =div-pack= update+delete handlers (§4) — silent
   no-redraw and delete crash.
5. =gtk-signal-focus!= else-clause, =gtk-make-scroller= orientation
   argument (§1/§5).
6. =%div-select= narrowing loop (§2) and the =%run-div-monad= /
   =diff-div= landmines (§2/§4) — latent today, but fix before relying
   on =use-vars= selection or the diff engine.

The reactive core (state-var → use-vars → dispatch → on-update) is
sound in shape; most of the "won't redraw" risk is concentrated in the
=div-pack= drawing branches and the (currently dead) =diff-div=
reconciler rather than in the dispatch machinery itself.
